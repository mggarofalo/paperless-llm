# Existing-OCR organization v2

V2 improves output validity and reduces broad tagging, but it is **not a
production-ready prompt**. The conservative policy misses clear date repairs,
still makes unsupported correspondent changes, and sometimes returns an allowed
taxonomy ID that does not match its own explanation. Repeating the same prompt
also changes substantive decisions.

This follows the [v1 experiment](2026-10-02-ocr-text.md). The
[frozen recipes and plan](../../eval/ocr-text-v2-2026-10-02/README.md) and
[aggregate results](../../eval/ocr-text-v2-2026-10-02/results.json) are available.
No live Paperless documents, production prompt, settings, or release changed.

## Design

300 independent calls: four arms of 75 cases, each using `gpt-6-luna` with medium
reasoning through the existing authenticated local Codex experiment runner.
Each call sees existing OCR, current metadata, and the full allowed taxonomy.
There are no images, tools, previous model transcriptions, or Paperless tokens.
Title and OCR must remain unchanged.

The same 25 real source documents and references from v1 produce three conditions:
original metadata; scored metadata removed; and scored metadata deliberately
wrong. Challenge titles are neutralized. Specific existing subject tags removed
from challenge copies provide 20 recovery targets per challenge condition, from
18 source documents. Two ambiguous dates and one correspondent remain unscored.
Thus each arm has 46 scored challenge dates, 48 correspondents, and 50 types.
Control metadata already matches the reference except for one type needing repair.

| Arm | Hypothesis |
| --- | --- |
| Baseline | Rerun unchanged v1 to measure contemporaneous performance |
| Contract | A complete no-change JSON template and final serialization checklist reduce invalid proposals |
| Policy | Add explicit date-evidence gates and provisional tag/type conventions |
| Policy repeat | Repeat the identical policy prompt and settings to measure variability |

All prompts, case files, references, and the plan were frozen before inference;
hashes were checked afterward. No edits or normalization followed model output.
The policy is a bundled hypothesis, not a factorial test of each individual rule.
It deliberately forbids new `household` and `personal` tags pending a user-defined
meaning; suppression of these tags is policy compliance, not learned precision.
Other rules distinguish primary documents from enclosures, transaction dates from
incidental dates, and specific subject tags from broad associations.

All documents were previously exposed. This is a development comparison, with
no fresh holdout and no production acceptance claim. Repeated conditions and runs
are not independent documents. The protocol follows the separation of criteria,
comparison, and error analysis described in [OpenAI's evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

## Raw results

All calls returned JSON; none timed out, used images, or truncated recorded
stdout/stderr. Every output kept title and OCR. No formatting cleanup was used.

| Validator-valid proposals | 63/75 | 74/75 | 74/75 | 74/75 |
| Challenge dates recovered | 32/46 | 34/46 | 26/46 | 29/46 |

Field recovery and tag recovery require the entire proposal to pass the existing
production validator. Extra additions count raw suggestions, including rejected
proposals. Reference-disagreeing writes count valid proposals and are not all
factual hallucinations: some reflect plausible but different taxonomy conventions.
Numerical ID matches also do not prove the model understood the corresponding
entity; see the audit below.

The baseline had 11 `keep_requires_null` rejections and one duplicate-tag
rejection. The other three arms each had one duplicate-tag rejection and no
schema failures. This supports the concrete serialization template, but does not
establish perfect contract compliance. V1 previously achieved 55/75 raw validity;
the unchanged baseline now reaches 63/75, illustrating run variability.

## Error audit

**Dates:** Contract-only still proposes an unsupported handwritten-check date,
with evidence acknowledging that the year is unclear. Both policy runs preserve
that date. However, the first policy run abstains on 20/46 challenge dates, and
the repeat on 15/46. Several misses have clearly printed dates, including full
four-digit years and an explicit notice-date label. One explanation incorrectly
treats the no-change template as a requirement to preserve a known wrong date.
This is over-abstention, not solely an OCR ceiling.

The first policy run has zero scored date miswrites. The repeat selects an
enclosed certification date instead of the primary application's date in all
three copies of one packet, including its control. These are real visible dates
assigned to the wrong document role. The zero-error result did not replicate.

**Correspondents:** Both policy runs change a correct correspondent on a poorly
recognized check, despite explanations expressing uncertainty or saying to keep.
In the wrong-field condition, one run also mistakes a bank logo for the relevant
party; the repeat emits an unrelated allowed ID while naming a financial provider
in its evidence. Better OCR would help the check, but cannot by itself repair the
contradiction between the proposed operation and the explanation.

**Taxonomy ID binding:** Both policy runs add a radon tag while explaining that
the subject is remodeling. The ID exists, so structural validation accepts it.
Other correspondent explanations similarly name entities different from the
selected ID. A membership check alone cannot catch this. Some existing numerical
reference matches can also conceal reasoning about a different issuer. Frozen
scores have not been relabeled after observing these errors.

**Types:** The policy corrects the preexisting contract classification in both
control runs, whereas baseline and contract-only leave it unchanged. Remaining
disagreements include tax demands classified as Invoice versus Record, transfer
confirmations as Record versus Statement, sermon notes as Record versus Note,
and insurance packets classified by different component documents. Some are
reasonable convention disagreements rather than invented facts. In particular,
the experimental transfer-confirmation rule can disagree with the frozen label;
the old reference remains unchanged so that disagreement stays visible.

**Tags:** Narrowing the policy sharply reduces extra additions while retaining
most removed labels. But remaining additions include receipts for checks or an
unpaid invoice, insurance inferred from an escrow item despite the narrower rule,
the wrong-ID radon additions, and one forbidden household addition. One duplicate
existing tag rejects a whole proposal in each policy run. Existing tag targets
are nonexhaustive: these figures measure recovery and suggestion volume, not
overall precision or tagging accuracy.

The audit inspected scored reference-disagreeing writes, date abstentions, and
extra additions, with OCR excerpts for material failures. Neither policy run
proposed sets for the ignored reference fields. This was not a new scan-level
relabeling or exhaustive evidence-quote verification of all otherwise passing
outputs.

## Repeatability and usage

Between the identical policy runs, proposed resulting dates agree on 65/75 cases,
correspondents on 69/75, types on 65/75, and tag sets on 69/75. All four agree
together on only **46/75**. This comparison ignores evidence wording and compares
proposals before validator gating; it is not an accuracy metric.

| Arm | Calls | Input tokens | Output tokens |
| --- | ---: | ---: | ---: |
| Baseline | 75 | 1,023,333 | 15,499 |
| Contract | 75 | 1,045,043 | 14,223 |
| Policy | 75 | 1,109,838 | 13,144 |
| Policy repeat | 75 | 1,103,705 | 13,279 |
| Total | 300 | 4,281,919 | 56,145 |

Usage comes from recorded stage provenance. Calls used existing ChatGPT
subscription authentication, with no separately billed API fallback. Private
inputs and outputs remain outside the repository.

## Decision

Do not promote the full v2 prompt. Keep the serialization-template finding and
the evidence that narrower subject-tag definitions reduce excessive additions.
The date gate is too conservative and inconsistently followed; correspondent
errors and ID binding remain material risks.

A useful next experiment would change the output boundary: have the model
identify an exact allowed entity name (or name plus ID), then deterministically
resolve it or reject a mismatch. Separate candidate evidence from a final
keep/set decision so contradictory abstention text cannot silently accompany an
update. Test that change with both Luna and a bounded stronger-model comparison,
using the same one-call-per-document budget before considering another model
stage. Dates need a clearer primary-document rule and preservation-versus-repair
policy. Confirm subjective taxonomy conventions and evaluate on fresh documents
before drawing deployment conclusions. These are recommendations, not changes
implemented by this experiment.
