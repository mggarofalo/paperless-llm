# Organization from existing OCR, 2026-10-02

This diagnostic isolates organization from image reading and OCR replacement.
It follows the [context search](2026-10-01-context-search.md), whose combined
scores obscured the difference between transcription failures and organization.

## Protocol

One `gpt-6-luna` call at medium reasoning processes each case. The input contains
the saved Paperless OCR, current metadata and full allowed taxonomy. No images,
visual transcription drafts, tools or reference answers are supplied. Title and
OCR must remain unchanged. The model can propose a date, correspondent, document
type and additive subject tags, with supporting quotes from the OCR.

The 25 previously inspected documents each appear in three conditions (75 calls):

- Control: original metadata and tags.
- Missing: scored non-null date/correspondent/type targets are cleared.
- Wrong: the correct date is shifted one year forward, and correspondent/type
  are replaced with the first allowed taxonomy ID different from the reference.

Challenge copies use a neutral filename title to avoid giving the answer through
an already-curated title. Their existing subject tags named receipts, insurance,
medical, cars, citizenship or taxes are removed and become recovery targets.
There are 36 challenge cases with at least one removed tag. Other tags, including
receipt logging and property/workflow state, remain unchanged. These are private
evaluation copies; no live Paperless document is edited.

Date, correspondent and type targets come from the earlier audited references;
ignored fields remain unscored. The known OCR key-fact label mistakes from the
previous study are irrelevant here: OCR is required to remain unchanged and is
not scored for transcription quality. Missing and wrong metadata are changed
together, so this is not an independent causal test of each input field.

The prompt, cases, recipe and protocol were hashed before inference. There is one
run, no adaptive prompt tuning, and no new holdout. All 25 source documents were
previously exposed. Results are a diagnostic of this fixed configuration, not a
production acceptance claim.

## Measurement

Field correctness is reported separately from valid proposals, incorrect writes,
successful repairs and abstentions. A valid proposal that keeps a missing or
wrong field fails recovery, but may be the appropriate behavior when the saved
OCR cannot support a value. A disagreement with a reference is not automatically
a fabricated fact; ambiguous dates and taxonomy choices need source review.

Tag recovery measures restoration of selected existing subject labels. Those
labels are not an exhaustive inventory of all reasonable tags, and existing tag
membership is not proof that the OCR alone establishes it. Extra tags are reported
as additions outside the recovery target and assessed separately. The control
condition tests restraint rather than positive tag recall.

## Results

All 75 calls returned JSON, with no transport failures. All kept OCR and titles
unchanged. Only **55/75 proposals passed the existing validator**. Eighteen
contained `keep` fields with non-null values; one re-added an existing tag and one
omitted required evidence for a set field. The validator rejects the whole proposal,
so an invalid tag or field also prevents credit for otherwise correct fields.

Raw results under the unchanged validator:

| Condition | Valid proposals | Date correct | Correspondent correct | Type correct |
|---|---:|---:|---:|---:|
| Control | 18/25 | 15/23 | 17/24 | 16/25 |
| Missing | 19/25 | 16/23 | 19/24 | 18/25 |
| Wrong | 18/25 | 14/23 | 17/24 | 15/25 |

To separate the interpretation problem from serialization, a **post-hoc diagnostic**
changed only values on `keep` fields to null in the 18 proposals rejected for that
reason. Actions, set values, tags, evidence and uncertainty were untouched. Original
outputs and primary scores remain intact. This is not an installed worker change
or a new model run. Revalidation exposed two additional duplicate-tag failures,
leaving **71/75 valid**: three duplicate-tag proposals and one missing-evidence
proposal still failed.

Results after that limited cleanup, still rejecting each remaining invalid proposal:

| Condition | Valid proposals | Date correct | Correspondent correct | Type correct |
|---|---:|---:|---:|---:|
| Control | 23/25 | 19/23 | 22/24 | 21/25 |
| Missing | 24/25 | 17/23 | 22/24 | 21/25 |
| Wrong | 24/25 | 17/23 | 20/24 | 17/25 |

The control type target requires one correction; other scored control fields already
match their references. Two dates and one correspondent have no unambiguous target
and are excluded from the field denominators.

### Interpretation of field results

- **Correspondent:** 42/48 challenge fields recovered after cleanup. The remaining
  six comprise five abstentions and one invalid proposal. Four abstentions concern
  poorly recognized checks; one leaves an incorrect correspondent despite a clearly
  named retailer in the OCR. There were no reference-disagreeing correspondent set
  values among the valid normalized proposals.
- **Date:** 34/46 challenge fields recovered. Eight abstentions occur where the
  saved OCR does not establish the transaction date. Two choose a real date from a
  secondary certification instead of the original application, and two proposals
  are invalid. In controls, that packet-focus disagreement recurs, and a handwritten
  check produces a definite bad date change despite evidence explicitly admitting
  ambiguity. This is a model decision failure as well as an input-quality problem.
- **Type:** 38/50 challenge fields recovered. Six set values disagree with references,
  four abstain, and two proposals are invalid. Disagreements include cover letter
  versus statement, application versus enclosed certification, tax notice versus
  invoice, and transfer confirmation versus record. These require clearer taxonomy
  policy; they are not all fabricated factual claims. The unchanged control also
  misses a warranted correction to Contract.

### Tags

After cleanup, Luna recovered **19/20 removed labels in each challenge condition**;
the raw validator credited 18/20 and 16/20 respectively. These are two presentations
of the same 18 source documents with removed tags, not 40 independent documents.
The unrecovered label is medical for a check whose OCR lacks clear service context.

Across all raw proposals, 46 tag additions fall outside the frozen recovery targets
(17 control, 16 missing, 13 wrong). Thirty are `household`. Many are plausible
subject associations, such as groceries or home-related documents, but they are
broader than the existing organization. Others stretch the taxonomy, including
school for a driver-training certificate and receipts for a check. Three proposals
try to re-add existing tags. **95% recovery is not 95% overall tagging accuracy.**
Tag definitions and tolerance for broad additions need to be explicit before judging
these additions as correct or incorrect.

## Conclusion

This supports continuing with Luna for a narrower organization workflow. It does
not support the earlier inference that OCR-replacement failures alone require a
larger model for organization. Correspondent recovery and recovery of existing
subject tags are promising; existing OCR quality and taxonomy policy explain many
misses. A real date regression and output-contract failures remain.

The next implementation should address the `keep` representation deterministically,
define the broad subject/type labels, and establish a policy for replacing populated
dates. Paperless OCR settings can then be evaluated on the cases where text is
missing or corrupted. None of those changes was made by this experiment. A larger
model comparison should use the same narrow task and report abstentions separately
from harmful updates, rather than reintroducing full transcription.

This one-run diagnostic is not a production acceptance test or an estimate of
accuracy on newly scanned documents. No prompt was tuned after seeing results.

## Expenditure

There were **75 model calls**, with **1,026,831 recorded input tokens** and
**15,931 output tokens**. The cleanup and rescoring used no model calls. These are
CLI-reported token totals, not a bill or an estimate of uncached usage. The existing
ChatGPT authentication was used; there was no separately billed API fallback.
